## 本项目采用的实现

### 团队邀请与加入审批

入口：我的团队 → 团队设置与加入审核；成员页也有相同入口。只有团队管理员可以设置邀请和审核申请。

- 保留已有邀请码接口，旧团队未设置策略时仍可直接加入，默认角色仍是学生成员。
- 管理员可以关闭邀请、设为1天/7天/30天/长期有效、重新生成邀请码、开启加入审核。
- 关闭、到期和重置都会阻止之后使用旧邀请加入。已有成员不受影响；已提交的申请可单独审核。
- 开启审核后，申请人先看到等待状态，不能提前读取团队项目。重复申请更新同一记录；管理员同意后只授予学生成员身份，不能在加入表单里自选老师或管理员。
- 我的团队显示本人的申请状态；管理员在设置页处理待审核申请。拒绝后可使用当前有效邀请码重新申请。
- 审核和轮换均锁定团队行，避免两个管理员重复审核或旧码与重置交叉成功；设置带版本号，旧窗口不能覆盖新设置。

课程简化：没有部门架构、短信邀请、多级审批或独立审批设计器。角色提升仍沿用原管理员操作，保留“至少一位管理员”的限制。

### 团队归档与解散

入口：团队设置 → 团队归档与解散。

1. 先将团队全部项目归档，再归档团队。
2. 归档保留阅读，并暂停邀请、新项目、成员角色调整、新预约与预约审批；可以恢复团队。已获批预约的申请人仍可取消自己的预约。
3. 归档后才能展开解散操作。必须先读取范围，明确项目、文档、任务、成员关系、预约和占用数量，再输入完整团队名称确认。
4. 服务端重新核验管理员身份、归档状态、项目状态、完整名称及预览令牌；范围已变化时必须重新核对。
5. 数据库级联清理团队项目、项目内私人文档、项目助手记忆、个人项目计划等，同时显式清理无直接外键的评论反应记录。

解散**不删除个人账号、全局个人 AI 记忆、个人课表或其他团队数据**。附件元数据随项目级联删除，磁盘孤立文件由全站清理机制回收。团队归档不宣称存量所有子页面都完全只读：项目原有归档限制继续生效，本轮额外约束新增、邀请及预约审批。

### 资源预约、审批与冲突

入口：我的团队 → 资源预约与占用。

- 原“实际占用登记”及 API 保留；新增的“计划预约”单独展示，避免把申请当作已经使用的记录。
- 申请只填资源名称、用途、开始和结束时间。按北京时间输入，结束须晚于开始，最长30天，不能预约过去时段。
- 学生、老师、管理员均可申请；老师和管理员可批准或拒绝；申请人可取消自己的待批或获批预约。
- 状态为待审批、已批准、已拒绝、已取消。备注选填，直接在列表完成审批，无需额外审批流程页面。
- 同一团队内按统一化的资源名称检查冲突，忽略全半角、首尾及连续空格、英文字母大小写差异。相邻时段允许衔接。
- 提交和批准时都检查获批预约与实际占用；批准时通过资源事务锁再检查一次，两个同时进行的重叠审批最多一个成功。
- 待审批申请暂不锁定时段。与已获批记录冲突的申请保留待审批并显示具体冲突原因，便于申请人取消后重新调整；没有照搬飞书的自动拒绝所有竞争申请。
- 实际使用人可登记自己获批的时段，其他成员不能通过实际占用登记覆盖该获批时段。
- 团队之间独立检查、独立展示，不透露其他团队的资源名称、用途或预约人。

本版资源是团队内按名称登记的共享资源，不把两个不同团队恰好相同的“GPU-01”当作同一台真实设备。若以后学校统一管理设备，需要另建校园资源目录及跨团队授权，不能直接合并现有名称。

附件建议：限制文件大小与类型；图片和 PDF 可站内预览，PPT 等不适合浏览器直接解释的格式提供下载；上传前给出限制和结果反馈，不增加封面商城、插件来源或复杂网盘层级。外部链接不能因为显示预览就被认定为已上传，第三方权限也不能绕过。

趋势建议：真实记录每天的剩余主任务及总量，明确采样起始日期，区分完成下降和范围增加。不根据今天的状态倒造以前的曲线；没有历史样本时直接显示“从开始采样后积累”，不要制造看起来完整的假燃尽图。

这里观察了官方说明与其页面图片，没有登录 Trello 上传附件，也没有登录 Jira 修改一个真实迭代。上传鉴权和采样事务的正确性须由本项目自身测试来证明，不能由产品帮助页代替。
